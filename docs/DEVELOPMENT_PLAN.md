# 双人魔法城堡：开发方案与验收用例

日期：2026-09-10。用户最终确定 **Unity + C#**，游戏脚本、编辑器工具与测试统一使用 C#。已编写 M1 输入、移动、共享镜头与 M2 冰火训练场源码，但尚未在 Unity 中编译运行。当前技能限于自动瞄准单个木桩的冰击、火击与破冰；下文的移动技能、敌人 AI、关卡和 Boss 仍是后续设计。

## 最新技术决策：Unity + C#

- 继续采用 Unity 6.3 LTS + URP，由本机编辑器创建实际工程并锁定版本。
- 第一单元交付导入源码，不手写或冒充编辑器生成的完整项目设置。
- 首版为本地双人：两个手柄，或一个键盘加一个手柄。
- M1 使用 Input System 直接绑定设备 ID，避免同一设备串号；后续需要重映射时再引入完整 Input Actions 配置。
- M1 的共享镜头使用自有 C# 相机脚本，暂不引入 Cinemachine；两名玩家完整碰撞边界参与构图。
- Python 路线已由用户取消，项目不增加 Python 运行时、服务端或桥接依赖。

当前源码范围、导入步骤和待执行验证见 [M1 原型说明](M1_SETUP.md) 与 [M2 战斗说明](M2_SETUP.md)。

## 1. 首版目标

两名玩家分别控制冰霜法师与火焰骑士，共同闯过城堡走廊、元素机关和守卫战，最后击败一名需要配合才能破防的城堡守护者。

首版做一段目标时长 10–15 分钟的完整体验。验收要能从角色加入、开始关卡、通关或失败重试一直走到结算。时长是设计目标，需要真实试玩测量。

| 维度 | 提议 |
| --- | --- |
| 引擎 | Unity 6.3 LTS，具体补丁和包版本在工程创建时锁定 |
| 画面 | 3D 场景 + 俯视共享镜头；具体角度通过原型调节 |
| 平台 | 先验收 Windows 桌面版；macOS 按需求追加独立构建验证 |
| 输入 | 两个手柄优先，键盘加手柄作为兼容组合 |
| 联机 | 首版本地双人；如要求异地联机，调整第一里程碑 |
| 内容 | 两名角色、两个普通敌人类型、三个挑战房间、一个 Boss 房 |
| 循环 | 观察危险 → 分工处理 → 合作完成 → 检查点 → 下一房间 |

## 2. 两名角色的原创技能方案

| 角色 | 普通攻击 | 核心技能 | 移动技能 | 合作任务 |
| --- | --- | --- | --- | --- |
| 冰霜法师 | 冰弹 | 短时冻结普通敌人或指定机关 | 短距离闪现，合法落点检测 | 制造控制窗口、稳定机关、标记 Boss 弱点 |
| 火焰骑士 | 近战挥击 | 火焰重击 | 冲刺，检测沿途碰撞 | 消耗冻结标记触发破冰、击退敌人、启动能量装置 |

初版每个角色先实现普通攻击和一个关键能力；通过测试后再增加完整移动技能。不要同时制作大量技能树。

建议的组合技为“冻结 → 火击 → 破冰”。冻结标记由火击消耗一次，触发附加伤害与独立反馈。冻结过期、同一攻击多次碰撞、Boss 免疫和队友伤害都需要明确规则。具体伤害与冷却后续调参。

两名角色都应能应付普通小怪；强制合作主要落在机关和 Boss 破防窗口，避免一位玩家失误导致另一位完全无法操作。

## 3. 首关流程

| 区域 | 目的 | 玩家行为 | 通过条件 |
| --- | --- | --- | --- |
| 入口准备区 | 学习操作 | 两人加入、移动、攻击训练目标 | 两人确认准备 |
| 房间一：守卫走廊 | 验证基本战斗 | 法师控制，骑士处理近战威胁 | 清除当前波次，二人抵达出口 |
| 房间二：元素闸门 | 验证非战斗配合 | 一人冻结机关转子，另一人启动火焰装置 | 两项条件在有效窗口内满足 |
| 房间三：混合守卫 | 验证分工与走位 | 面对近战追击者和远程施法者，利用组合技 | 清除敌人，获得 Boss 前检查点 |
| Boss 房：城堡守护者 | 综合运用 | 避开预警，冻结弱点，再由火击破甲 | 击败 Boss，二人进入结算 |

这条路线是原创开发方案。原作的地图布局、Boss 流程和关卡时长没有在本次调研中逐帧核实。

Boss 首版只做一个完整阶段：预警攻击、暴露弱点、合作破防、输出窗口、恢复护甲。循环稳定后再增加第二阶段，避免提前堆叠内容。

## 4. 模块与关键状态

| 模块 | 责任 | 关键状态或数据 | 主要验收点 |
| --- | --- | --- | --- |
| 玩家与输入 | 设备绑定、加入、退出、动作输入 | playerId、设备、角色选择、输入意图 | 一个设备不同时控制两名角色 |
| 角色运动 | 移动、冲刺或闪现、合法位置 | 位置、朝向、移动状态、碰撞层 | 高速移动不穿越实心墙，不落到地图外 |
| 共享相机 | 跟踪两人、边界与遮挡处理 | 双人位置、构图范围、镜头边界 | 两名角色和主要危险尽量同时可见 |
| 战斗与技能 | 命中、伤害、冷却、控制状态 | 技能配置、攻击实例、受击目标、冻结标记 | 同一攻击不会因多个碰撞体重复结算 |
| 敌人与 Boss | 追踪、攻击预警、阶段变化 | 当前状态、目标、生命、阶段 | 预警结束前不结算对应伤害 |
| 机关与房间 | 波次、开门、双人触发、重置 | 房间状态、机关状态、完成标记 | 失败重试可恢复到一致状态 |
| 复活与检查点 | 倒地、恢复、团灭、重新开始 | 玩家存活状态、最近检查点 | 不出现门已关而敌人已消失的卡关状态 |
| UI 与声音 | 血量、技能状态、目标和反馈 | 两人的状态、当前任务 | 颜色、图标和音效共同传递危险与成功 |

建议将输入转换为动作意图，战斗状态由游戏逻辑更新，再驱动动画和特效。这样可以单独验证规则，也方便后续接入联网；但这不意味着联网可以自动完成，权威状态、延迟和断线仍需专门设计。

技能、敌人和房间使用配置与运行时状态分离的方式。静态配置可以使用 ScriptableObject；单局生命值、冷却等保存在各实例中，避免共享资产让两个玩家互相覆盖状态。[Unity ScriptableObject 文档](https://docs.unity3d.com/6000.0/Documentation/Manual/class-ScriptableObject.html)

## 5. 开发顺序与小单元

先批准整体方向，随后每个编码单元先给出涉及文件、行为和验收方法；超过三个文件时继续拆分。下表是里程碑，不代表一个提交要包含全部内容。

| 里程碑 | 小单元 | 可以交付的结果 | 完成条件 |
| --- | --- | --- | --- |
| M0 立项与仓库 | 确认平台与输入；建立仓库；记录引擎版本 | 文档仓库与明确的首版目标 | 新成员可理解如何开始 |
| M1 双人灰盒 | 引擎生成工程；单角色移动；双设备绑定；共享镜头 | 两人可在简单场景独立移动 | 无输入串号、无相机丢人、无明显穿墙 |
| M2 战斗闭环 | 单次命中规则；技能冷却；冻结；破冰；一个敌人 | 两人可合作击败敌人 | 冻结可消费一次，反馈清楚 |
| M3 关卡闭环 | 房间状态；双人机关；复活；检查点 | 三个房间可连续游玩 | 清场开门与失败重置均正常 |
| M4 Boss 与美术 | Boss 状态；预警；合作破甲；城堡与角色替换 | 一段完整城堡冒险 | 从开始到结算可连续完成 |
| M5 构建与试玩 | 桌面构建；手柄回归；性能采样；新玩家试玩 | 可分发测试包与问题列表 | 至少完成约定设备上的完整流程验证 |

第一段最小演示建议只做 M1 加“一只训练敌人、一次冻结、一次火击破冰”，用它判断手感和配合是否成立。通过后再扩展关卡。

## 6. 仓库组织方案

当前资料包已包含 `UnityImport/Assets/MagicCastle/` 下的 Runtime、Editor、Tests 源码，以及 README、协作规则和设计文档。以下 `game/` 布局是本机编辑器创建完整项目后采用的目标结构，当前尚无 ProjectSettings、场景文件或构建产物。

| 路径 | 作用 |
| --- | --- |
| `README.md` | 项目说明、启动方法、当前状态 |
| `docs/` | 调研、设计、决策与验收记录 |
| `game/Assets/_Game/` | 场景、脚本、预制体、静态配置、UI 和自有资源 |
| `game/Assets/Tests/` | 核心逻辑与场景交互测试 |
| `game/Packages/` | Unity 包依赖与锁定文件 |
| `game/ProjectSettings/` | 编辑器版本和项目设置 |
| `art-source/` | 自制 Blender 等源文件 |
| `CLAUDE.md` | 项目协作约定与用户纠正后的规则 |

Unity 工程应由所选编辑器创建，以实际可打开的工程为起点。将引擎必需设置与 .meta 文件一同跟踪；缓存、临时导出和日志按引擎规则忽略。美术大文件引入前再配置 Git LFS，避免把缓存或完整录像放入源码仓库。

分支建议使用 `main` 加短期功能分支，每个提交对应可说明、可验证的小目标。是否公开源码和采用何种项目许可证暂不决定。

## 7. 如果首版就要在线双人

将 M1 调整为“两台机器加入同一房间并移动”，随后立刻验证一次远程技能命中和状态同步，再继续内容开发。

| 事项 | 建议 |
| --- | --- |
| 权威规则 | 明确由主机或服务端决定伤害、敌人、机关和通关状态 |
| 网络对象 | 稳定标识角色、敌人、投射物和机关 |
| 连接流程 | 创建房间、加入、版本校验、退出与错误提示 |
| 交互体验 | 移动插值、技能反馈、重复消息处理、迟到消息处理 |
| 异常边界 | 客户端退出、主机退出、场景切换中断；首版可提示重开，不默认承诺主机迁移 |

Unity 官方 [Boss Room](https://github.com/Unity-Technologies/com.unity.multiplayer.samples.coop) 可用于研究技能与服务端权威同步。项目 README 中的“本地多人测试”是多实例网络测试，不能直接理解为同一进程的双手柄同屏支持。

## 8. 潜在问题与验收用例

以下均为计划执行的用例。当前已具备 M1 / M2 源码、16 个 Unity EditMode 用例和 21 个独立 C# 核心检查；环境没有 Unity / .NET SDK，首次 GitHub Actions 在测试步骤启动前失败，因此不声明这些测试已通过。具体状态见 M2 文档。发现实际 bug 后，应先增加能够复现该问题的最小测试，再修复并回归。

| ID | 风险或场景 | 操作 | 期望结果 | 验证方式 |
| --- | --- | --- | --- | --- |
| T01 | 输入串号 | 两个手柄分别加入并同时移动 | 两名玩家各自响应对应设备 | Play Mode 与真机 |
| T02 | 第三设备加入 | 双人已就绪后操作第三个设备 | 不生成第三名角色，不抢占已有绑定 | Play Mode |
| T03 | 手柄断开 | 游戏中拔掉并重新接入一个手柄 | 提示或暂停符合设计，恢复后仍控制原角色 | 真机 |
| T04 | 镜头拉扯 | 两人走向房间相反角落 | 按边界策略保持可见，不无限缩小画面 | 场景试玩 |
| T05 | 重复命中 | 同一攻击同时触碰敌人的多个碰撞体 | 仅按设计结算一次 | 自动化核心测试 |
| T06 | 冷却绕过 | 冷却期间连续触发技能输入 | 不能额外施放，也不会延后错误重放输入 | 自动化核心测试 |
| T07 | 冻结标记消费 | 先冻结，再让两个火焰命中几乎同时发生 | 破冰只触发一次，后续为普通命中规则 | 自动化核心测试 |
| T08 | 冻结过期 | 冻结结束后再执行火击 | 不触发已过期的组合技 | 自动化核心测试 |
| T09 | 冲刺穿墙 | 对薄墙、拐角和门边反复冲刺 | 不能穿越不可通行实体 | 物理场景测试 |
| T10 | 闪现非法落点 | 向墙内、地图外与落差边缘闪现 | 拒绝或调整到合法位置，规则一致 | 物理场景测试 |
| T11 | 双人机关卡死 | 同时触发、提前离开、完成时倒地 | 机关只完成一次；失败后可以重新尝试 | Play Mode |
| T12 | 团灭状态不一致 | 开门过程中两人均倒地并重试 | 玩家、敌人、门与机关回到同一检查点状态 | 集成测试 |
| T13 | Boss 阶段跳变 | 破甲窗口结束时发生多次命中 | 阶段切换一次，伤害规则明确 | 自动化与场景测试 |
| T14 | 通关重复触发 | 两名玩家几乎同时进入出口 | 仅进入一次结算，不重复保存 | 集成测试 |
| T15 | 构建缺依赖 | 在约定设备上启动独立构建 | 无需编辑器即可完成整关 | 构建验收 |
| T16 | 战斗表现拥挤 | 两人和全部首版敌人同时施放技能 | 关键预警可辨认，并记录帧时间与尖峰 | 试玩与性能采样 |
| T17 | 网络异常，仅在线版 | 注入约 100 ms RTT、抖动和少量丢包 | 不重复伤害、不越过机关条件，记录操控感受 | 网络模拟与真机 |

除功能问题外，最大的项目风险是范围扩大和美术制作拖延。用“最小组合技演示 → 一间房 → 一段完整流程”的验收顺序控制投入；性能目标在选定最低设备后制定，不能仅凭编辑器观感承诺帧率。

## 9. 后续工作

当前已确认方向：`magic-castle-coop`、Unity + C#、3D 俯视、本地双人、桌面首版、冰火合作的短篇城堡冒险。用户提供的实际 GitHub 仓库为公开仓库，本次沿用其现有可见性。

先在本机创建工程并完成 M1 / M2 验收，重点验证设备隔离、碰撞、射程、遮挡、冻结消费与暂停恢复；随后加入敌人预警攻击、玩家生命值及复活。每个新改动单元仍按协作规则拆分；既有技术决策不重复确认。GitHub 已可访问，代码按小单元提交。
